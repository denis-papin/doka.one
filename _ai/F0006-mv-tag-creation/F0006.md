# Goal
Let a client **define** a multi-valued (MV) tag and **see it when listing the
system's tags**, through the two existing tag endpoints. An MV tag is a tag
whose future values are a **set drawn from a bounded vocabulary** (e.g. a
`color` tag whose vocabulary is `BLUE, GREEN, RED`).

This spec covers **two distinct capabilities**, each evolving one endpoint:

| # | Capability      | Endpoint to evolve                        | Handler                        |
|---|-----------------|-------------------------------------------|--------------------------------|
| 1 | Create an MV tag | `POST /document-server/tag`              | `add_tag` → `TagDelegate::add_tag` ([`tag.rs`](../../document-server/src/tag.rs)) |
| 2 | List MV tags     | `GET /document-server/tag`               | `get_all_tag` → `TagDelegate::get_all_tag` ([`tag.rs`](../../document-server/src/tag.rs)) |

This is the **foundation only**: writing an item's set and filtering on it are
specified separately by [F0007](../F0007-tag-multi-value/F0007.md) and are out
of scope here.

# Gap
The tag endpoints know only the seven scalar types, and nothing about a
vocabulary — on **both** the create and the list side.

- **Create (`POST /tag`) rejects the type.** `TagType::from_str`
  ([`web_types.rs`](../../dkdto/src/web_types.rs)) has no `"multi"` arm:
  ```rust
  match s {
      TAG_TYPE_TEXT => Ok(TagType::Text), /* … the six other scalars … */
      _ => Err(()),               // "multi" lands here today
  }
  ```
  so `check_input_values` ([`tag.rs`](../../document-server/src/tag.rs))
  turns a `"multi"` request into `INCORRECT_TAG_TYPE`. There is also no request
  field for the vocabulary (`AddTagRequest`
  [`web_types.rs`](../../dkdto/src/web_types.rs) is `{ name, tag_type,
  default_value }`) and no column to store it (`tag_definition`
  [`schema_cs.ddl`](../../admin-server/resources/schema_cs.ddl) has no list
  column; `insert_tag_definition` [`tag.rs`](../../document-server/src/tag.rs)
  writes `name, string_tag_length, default_value, type` only).

- **List (`GET /tag`) drops the vocabulary.** The list handler runs
  `search_tag_by_id(tag_id = None)`
  ([`tag.rs`](../../document-server/src/tag.rs)); it and the shared row
  mapper `map_current_row_to_tag` ([`tag.rs`](../../document-server/src/tag.rs))
  `SELECT`/build only `id, name, type, string_tag_length, default_value`, so
  even a stored vocabulary would never reach the response. A listed MV tag would
  look like a bare `"multi"` tag with no allowed values.

# Shared changes (foundation for both capabilities)

Both endpoints depend on the same small set of type/schema additions. They are
specified once here and referenced by rule id (`S1`…`S5`) from each capability.

- **`S1` — the `Multi` tag type.** Add `TagType::Multi`
  ([`web_types.rs`](../../dkdto/src/web_types.rs)) and a
  `TAG_TYPE_MULTI = "multi"` const; `from_str` accepts `"multi"`, `as_str`
  returns `"multi"`. The type is stored in the **existing**
  `tag_definition.type varchar(25)` column — no new "type" column.
- **`S2` — vocabulary on the request.** `AddTagRequest` gains
  `predef_values: Option<Vec<String>>` ([`web_types.rs`](../../dkdto/src/web_types.rs)).
- **`S3` — vocabulary on the response.** `TagElement` gains
  `predef_values: Option<Vec<String>>` ([`web_types.rs`](../../dkdto/src/web_types.rs)).
- **`S4` — one new schema column (confirmed).** The **sole** schema change:
  ```sql
  ALTER TABLE tag_definition ADD COLUMN predef_values text[];
  ```
  Stores the vocabulary as a PostgreSQL text array; `NULL` for non-`Multi` tags.
  No other column is added or altered; `tag_value.value_multi` and the whole
  item-value / filter machinery are **F0007**.
- **`S5` — new error code.** Add `BAD_TAG_DEFINITION` to
  [`error_codes.rs`](../../dkdto/src/error_codes.rs) (does not exist yet); F0007
  reuses it.

# Capability 1 — Create an MV tag

**Endpoint to evolve:** `POST /document-server/tag`
(handler `add_tag` [`main.rs`](../../document-server/src/main.rs) →
`TagDelegate::add_tag` [`tag.rs`](../../document-server/src/tag.rs) →
`check_input_values` [`tag.rs`](../../document-server/src/tag.rs) →
`insert_tag_definition` [`tag.rs`](../../document-server/src/tag.rs)).

## Inputs — `AddTagRequest`

| Field           | For a `Multi` tag                                       | For a scalar tag (unchanged) |
|-----------------|--------------------------------------------------------|------------------------------|
| `name`          | tag name, same rules as today                          | tag name                     |
| `tag_type`      | the new keyword `"multi"` (`S1`)                        | `text`/`bool`/`int`/…        |
| `predef_values` | `Some(vocabulary)`, a non-empty `Vec<String>` (`S2`)   | must be `None`               |
| `default_value` | ignored (a default set is out of scope)                | as today                     |

## Rules

1. **Accept the `"multi"` type.** With `S1`, `POST /tag` carrying
   `tag_type = "multi"` is no longer rejected as an unknown type.
2. **Require a valid vocabulary.** In `check_input_values`, for a `"multi"` tag
   `predef_values` must be `Some` and **non-empty**; every element must be
   non-blank after trimming (length ≥ 1); **duplicates are rejected**. Any
   violation → `BAD_TAG_DEFINITION` (`S5`).
3. **Reject a vocabulary on scalar tags.** For any non-`Multi` type,
   `predef_values` must be **absent** (`None`); supplying it →
   `BAD_TAG_DEFINITION`.
4. **Persist the vocabulary.** `insert_tag_definition` adds `predef_values` to
   the insert (`S4`), binding the vocabulary for a `Multi` tag and `NULL`
   otherwise:
   ```sql
   INSERT INTO cs_<customer>.tag_definition(name, string_tag_length, default_value, type, predef_values)
   VALUES (:p_name, :p_string_tag_length, :p_default_value, :p_type, :p_predef_values)
   ```
   `default_value` is ignored for `Multi`.
5. **Scalar creation is unchanged.** The seven scalar types keep their exact
   creation/validation behaviour; an unknown keyword still returns
   `INCORRECT_TAG_TYPE` ([`error_codes.rs`](../../dkdto/src/error_codes.rs)).

## Errors

| Condition                                                      | Stage that rejects              | Outcome                             |
|---------------------------------------------------------------|---------------------------------|-------------------------------------|
| `"multi"` with `predef_values` missing / `None`               | `check_input_values` (`tag.rs`) | 400 — `BAD_TAG_DEFINITION`      |
| `"multi"` with empty vocabulary `[]`                          | `check_input_values`            | 400 — `BAD_TAG_DEFINITION`          |
| `"multi"` with a blank element (`["RED", ""]`)               | `check_input_values`            | 400 — `BAD_TAG_DEFINITION`          |
| `"multi"` with a duplicate element (`["RED", "RED"]`)        | `check_input_values`            | 400 — `BAD_TAG_DEFINITION`          |
| `predef_values` supplied on a non-`Multi` tag                 | `check_input_values`            | 400 — `BAD_TAG_DEFINITION`          |
| Unknown `tag_type` (e.g. `"multivalue"`)                     | `check_input_values` (`from_str`) | 400 — `INCORRECT_TAG_TYPE` (unchanged) |
| Tag name not printable / too long                             | `check_input_values`            | 400 — `INCORRECT_CHAR_TAG_NAME` / `INCORRECT_LENGTH_TAG_NAME` (unchanged) |

## Examples — `POST /tag` request `(name, tag_type, predef_values)` → outcome

| Request                                        | Outcome                                                             |
|------------------------------------------------|--------------------------------------------------------------------|
| `("color", "multi", ["BLUE","GREEN","RED"])`  | 200 — created; `predef_values` stored as `{BLUE,GREEN,RED}`        |
| `("color", "multi", [])`                       | 400 — `BAD_TAG_DEFINITION` (empty vocabulary)                      |
| `("color", "multi", None)`                     | 400 — `BAD_TAG_DEFINITION` (missing vocabulary)                    |
| `("color", "multi", ["RED","RED"])`           | 400 — `BAD_TAG_DEFINITION` (duplicate element)                     |
| `("color", "multi", ["RED",""])`              | 400 — `BAD_TAG_DEFINITION` (blank element)                         |
| `("size", "text", ["S","M"])`                 | 400 — `BAD_TAG_DEFINITION` (`predef_values` on a scalar tag)       |
| `("size", "text", None)`                       | 200 — unchanged scalar creation                                    |
| `("color", "multivalue", …)`                  | 400 — `INCORRECT_TAG_TYPE` (unknown keyword) — n/a, rejected       |

# Capability 2 — List MV tags

**Endpoint to evolve:** `GET /document-server/tag?<start_page>&<page_size>`
(handler `get_all_tag` [`main.rs`](../../document-server/src/main.rs) →
`TagDelegate::get_all_tag` [`tag.rs`](../../document-server/src/tag.rs) →
`search_tag_by_id(None, …)` [`tag.rs`](../../document-server/src/tag.rs) →
shared mapper `map_current_row_to_tag` [`tag.rs`](../../document-server/src/tag.rs)).
`GET /tag` is the only public read endpoint for tags; there is no GET-by-id.

## Output — `GetTagReply`

Every tag in the customer schema, scalar and MV together, as
`GetTagReply { tags: Vec<TagElement> }`. Each `TagElement` carries the new
`predef_values` field (`S3`): `Some(vocabulary)` for a `Multi` tag, `None` for a
scalar tag.

## Rules

1. **Return the vocabulary.** `map_current_row_to_tag` reads the new column and
   `search_tag_by_id` adds `predef_values` to its `SELECT`, so `GET /tag`
   returns each `Multi` tag with `predef_values = Some(V)` and each scalar tag
   with `None` (`S3`, `S4`).
2. **Do not hide MV tags.** MV tags appear in the listing alongside scalar tags,
   with `tag_type = "multi"` and their vocabulary — no tag type is filtered out.
   A client can enumerate all tags and tell which are multi-valued and what each
   one's allowed values are.
3. **Paging and ordering are unchanged.** `GET /tag?start_page&page_size` keeps
   today's paging and `ORDER BY name`; only the extra column is added to the
   projection.
4. **Sibling read queries stay consistent.** `search_tags_by_names`
   ([`tag.rs`](../../document-server/src/tag.rs)) and `search_tag_by_name`
   ([`tag.rs`](../../document-server/src/tag.rs)) — used by the item/search
   flows, not by `GET /tag` — also select `predef_values` so every `TagElement`
   built anywhere is complete.

## Errors

No new request-level error path: listing cannot fail on account of an MV tag.
By construction (Capability 1, Rule 2) a stored `Multi` row always has a
non-empty `predef_values`; the read side does not re-validate that invariant.

## Examples — `GET /tag` after creating `color` (multi) and `size` (text)

| Tag listed | `tag_type` | `predef_values`          |
|------------|------------|--------------------------|
| `color`    | `"multi"`  | `Some({BLUE,GREEN,RED})` |
| `size`     | `"text"`   | `None`                   |

# Implementation surface

- [`dkdto/src/web_types.rs`](../../dkdto/src/web_types.rs) — `S1` (`TagType::Multi`,
  `TAG_TYPE_MULTI`, `from_str`/`as_str`/`value_column_name` arms), `S2`
  (`AddTagRequest.predef_values`), `S3` (`TagElement.predef_values`).
- [`dkdto/src/error_codes.rs`](../../dkdto/src/error_codes.rs) — `S5`
  (`BAD_TAG_DEFINITION`).
- [`admin-server/resources/schema_cs.ddl`](../../admin-server/resources/schema_cs.ddl)
  — `S4` (`ALTER TABLE tag_definition ADD COLUMN predef_values text[]`).
- [`document-server/src/tag.rs`](../../document-server/src/tag.rs):
  - **Capability 1** — `check_input_values` (Multi arm + "no vocab on scalar"
    guard); `insert_tag_definition` (write the column).
  - **Capability 2** — `map_current_row_to_tag` (read the column);
    `search_tag_by_id`, `search_tags_by_names`, `search_tag_by_name` (add
    `predef_values` to each `SELECT`).

**Not touched:** `tag_value` (no `value_multi` column here), the item
create/write path, the filter pipeline (`filter_ast` / `type_resolver` /
`generator`), search SQL, and every scalar tag path — all F0007.

# Out of scope

- **Writing an item's set** for an MV tag (`tag_value.value_multi`, off-vocabulary
  validation) — **F0007**.
- **Filtering** with `ANY` / `ALL` / `NONE` / `IS` — **F0007**.
- **A default value set** for an MV tag — later ticket if needed.
- **Editing** an existing tag's vocabulary (add/remove predef values) — later
  ticket; F0006 only creates and lists.
- **Deleting** an MV tag — `DELETE /tag/<tag_id>` already works and is unchanged.

# Integration tests

Black-box validation over the public API lives in a sibling
`integration_test_mv_tag_creation.md` (IT-F0006), implemented in
`doka-api-tests/tests/F0006-mv-tag-creation.rs`. Mandatory scenarios, grouped by
capability:

- **Create (`POST /tag`)** — create a `"multi"` tag with a vocabulary
  (200 + `tag_id`); reject missing / empty vocabulary; reject a duplicate or
  blank element; reject `predef_values` on a scalar tag; confirm an unknown type
  still returns `INCORRECT_TAG_TYPE`; confirm scalar creation is unchanged.
- **List (`GET /tag`)** — after creating one MV tag and one scalar tag, list all
  tags and confirm the MV tag appears with `tag_type = "multi"` and its
  vocabulary, while the scalar tag appears with `predef_values = None`.
